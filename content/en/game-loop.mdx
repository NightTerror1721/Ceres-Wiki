# The game loop

A game is, in essence, a loop: **read input → update → draw → wait for the next frame**.
`ceres/game.h` gives you that skeleton with two ways to measure time.

## The skeleton

```c
#include "ceres/game.h"

struct game g;
game_init(&g, 200000);          // one frame = 200000 instructions

while (g.running)
{
    game_frame_begin(&g);       // input_update() and the start mark

    update(&g);
    draw();

    game_frame_end(&g);         // wait out the rest of the frame
}
```

Or with functions:

```c
game_run(&g, update, draw, &state);
```

`game_quit(&g)` sets `g.running` to 0.

## Two ways to measure time

Ceres does not use a fixed clock: you choose.

<Tabs>
  <Tab label="Instruction budget">
The default mode. A frame is a number of **ticks** (instructions) and it waits with a spin on
`timer_ticks()`.

```c
game_init(&g, 200000);          // 200k instructions per frame
/* game_frame_end spins until the budget is used up */
```

It is **deterministic**: the same program does exactly the same thing on every run. It is what
tests and reproducible games want, and what lets you debug backwards. `game_over_budget(&g)`
tells you whether the last frame overspent.
  </Tab>
  <Tab label="Real time (sleeping)">
For a game that must run at a steady speed on a real clock. A frame lasts `ms` milliseconds
from its start; its own work counts, and a late frame is not made up for.

```c
game_init(&g, 0);
game_pace_ms(&g, 16);           // ~60 FPS, sleeping with the alarm (no CPU burned)
```

It needs no interrupt handler.
  </Tab>
  <Tab label="Real time (spinning)">
Like the previous one but **spinning** on the nanosecond clock, without sleeping. It needs no
`irq` module; it keeps the host busy and the frame ends at the clock's step rather than the
sleep's.

```c
game_init(&g, 0);
game_pace_real(&g, 16);
```
  </Tab>
</Tabs>

<Callout type="info" title="Which to use when">
| You want… | Use |
|---|---|
| Reproducible tests, identical physics | instruction budget |
| A 60 FPS game, portable, little CPU | `game_pace_ms` |
| A 60 FPS game without depending on the irq module | `game_pace_real` |
</Callout>

## The order matters

```
game_frame_begin()   → drains keyboard/mouse/gamepad and computes the edges ("just pressed")
   update()          → uses key_pressed/key_down, moves things
   draw()            → gfx_clear, paint, gfx_present
game_frame_end()     → waits for the next frame
```

A reliable pattern is a **state machine** inside `update`: `TITLE`, `PLAYING`, `PAUSED`,
`GAMEOVER`.

```c
enum state { TITLE, PLAYING, PAUSED, GAMEOVER };

static void update(struct game* g, struct game_state* s)
{
    switch (s->phase)
    {
    case TITLE:
        if (key_pressed(KEY_ENTER)) s->phase = PLAYING;
        break;
    case PLAYING:
        if (key_pressed(KEY_ESCAPE)) s->phase = PAUSED;
        move(s);
        break;
    case PAUSED:
        if (key_pressed(KEY_ESCAPE)) s->phase = PLAYING;
        break;
    case GAMEOVER:
        if (key_pressed(KEY_ENTER)) restart(s);
        break;
    }
}
```

## Physics with a fixed step

Even if your frame is not deterministic, you can make the **physics** deterministic by
updating in fixed tick steps. A classic accumulator:

```c
s->accumulator += elapsed_ticks;
while (s->accumulator >= STEP) {
    physics_step(s);
    s->accumulator -= STEP;
}
```

<Callout type="tip" title="Start with the instruction budget">
While developing, use `game_init(&g, N)`. Your game will be reproducible, tests will compare
outputs and you can rewind with the debugger. When it is ready, switch to `game_pace_ms` to
play comfortably.
</Callout>

## Pairing it with the framebuffer

`game.h` is only the **timing loop**: it draws nothing. The drawing goes in the `draw`
callback, and the pixel framebuffer (`ceres/fb.h`, video level V1) fits it directly. `game`
does **not** choose a video level, show or hide the cursor, or set raw input - you do that
before the loop:

```c
#include "ceres/video.h"
#include "ceres/fb.h"
#include "ceres/game.h"
#include "ceres/terminal.h"

static void update(struct game* g, void* ctx) { /* logic; game_quit(g) to leave */ }

static void draw(struct game* g, void* ctx)
{
    fb_clear(0x00102040);
    /* ...pixels... */
    fb_present();                 // swaps the buffers and waits for the VBlank
}

int main(void)
{
    video_set_level(VIDEO_BITMAP);       // V1: the bitmap plane
    video_set_resolution(320, 240);
    term_show_cursor(0);                 // no terminal cursor
    term_set_raw(1);                     // every key as it is pressed
    if (fb_init(320, 240) != 0) return 1;

    struct game g;
    game_init(&g, 200000);               // the game's frame budget, in CPU cycles
    game_run(&g, update, draw, 0);       // until game_quit

    fb_shutdown();
    term_set_raw(0);
    term_show_cursor(1);
    return 0;
}
```

<Callout type="info" title="fb_present already waits for the VBlank">
`fb_present()` swaps the buffers at the next vertical blank and waits for it, so a game drawn
with `fb_*` is paced by the screen whatever `game` does. `game_pace_vblank(&g, 1)` makes the
frame end at that same blank; with `game_pace_ms`/`game_pace_real` the frame is `ms`
milliseconds of machine time instead.
</Callout>

<Callout type="warn" title="input_update is not raw keys">
`game_frame_begin()` calls `input_update()`, which reads the **input module**
(`ceres/input.h`: keyboard, mouse, gamepad as continuous state and edges), not `key_*`. Set
`term_set_raw(1)` if you want raw keys, but read them with `input_*` in `update`, or call
`key_get()` after `game_frame_begin()`. Never mix raw mode with `scanf`/`fgets`.
</Callout>
